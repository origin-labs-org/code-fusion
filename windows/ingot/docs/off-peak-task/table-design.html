先选对观察视角

Off-Peak 不Yes单纯的Scheduled Tasks。它把One次UserTask拆成产品身份、Local控制、 Agent executeandService端准入四个层次；每层Answer的Issue不同。

01PRODUCT

User看到什么

SubmitOne次性Task，WaitingLow峰execute；无论Medium间续Run多少段，Task卡片and History 都保持One个身份。

02LOCAL CONTROL

Customer端控制什么

SQLite Save聚合Current态；Service 同步票据；Scheduler 负责认领、派发、超时回收and退避。

03AGENT RUNTIME

Task如何真正execute

首段创建 Session，后续段恢复同One Session；每次Model request都必须携带当段有效 ticket。

04SERVER GATE

谁Decide何时能Run

Service端维护 FIFO、Concurrencyand ticket Lifecycle。Customer端只观察Result，不CopyService端Queued真E。

推荐阅读顺序 Product → Local Service / Scheduler → Host / Agent → Server Gateway。 但Run时Status会反向回流：Service端票据Decide准入，Agent ResultDecideLocalFinal state，Local聚合再Decide UI。

普通 Automation 的同One定义会按周期产生很多次独立触发，runs 表既Yes幂等账本也Yes历史。 Off-Peak Current只有One次逻辑Run，重复发生的Yes ticket 分段。

CURRENT · V1

Continue只用聚合行

最少的表and写路径，足够CompletedOne次性Task、分段续Run与 0/1 History。

  • 优点：Model简单，Upgrade成本最Low
  • 代价：Old ticket 被覆盖
  • 代价：DeleteTask可能丢 settle Retry
NOT RECOMMENDED

如果One条Task仍然只Allow once逻辑execute，那么 task 与 run 永远接近 1:1，只会把同OneStatus拆写两遍。

  • 适合：未来支持重复触发同OneTask定义
  • 不适合：只为Save ticket 分段
  • 风险：History 语义被误改成 1:N
RECOMMENDED EVOLUTION

按需增加 off_peak_tickets

让聚合表ContinueAnswer“Task现在怎样”，子表专门记录“每张票怎样流转与核销”。产品 History 仍保持 0/1。
